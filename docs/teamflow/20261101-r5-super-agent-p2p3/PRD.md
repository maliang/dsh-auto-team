# r5 · 队长分层 + Inline & Spill + 内部 Trigger 总线（Super-agent 融入第二/三期合并）

## 1. 背景与目标

第一期（r4）让信息与信号都不必再穿过队长：上游产物直投下游成员、成员停滞能被面板看见。但队长本身仍是整条流水线上最贵、最容易僵住的一环：

- **队长没有自己的"档位"**：成员可以按角色配 provider/model/effort（`src/host/prompt.ts` 里队长段落只有工作流程，没有行为约束），队长却永远跑宿主默认模型，并且被鼓励「深度参与」——`captainSection`（`src/host/prompt.ts:14`）只说「先 plan 再 dispatch」，没有任何一句拦它亲自跑活。队长一旦调 `bash` 跑一个前台长命令，整个编排就僵在那里等它返回。
- **记忆注入只会在预算边缘丢弃信息**：`src/host/memory/inject.ts`（234 行）按 4000 字预算拼正文，超了直接截断并追加 `…[截断]` + 尾行说明（`inject.ts:35`、`:154-167`）。成员拿到的是"半段正文 + 一个说明"，不知道被丢的是什么，也无法按需取回——实测注入已到 3970/4000，任何新增内容都要靠丢旧内容换。
- **事件在观测、但没驱动任何决策**：`tools/result`、`agent/status`、`subagent/end`、`agent/error` 这些宿主事件，r4 只用了其中一个信号（`lastProgressAt`）。门禁失败、成员退出、依赖完成、超时无产出这四类「本该自动推动队长」的事，今天全都躺在账本里等人看。

本期把原方案的第二期（§3.5 + §3.4）与第三期（§3.3）合并交付。合并的代价必须点明：原方案把 Trigger 排在后面，是为了先拿到「Fast 层到底能过滤掉多少」的真实数据。既然合并，**Fast 层就必须保持最小**——只做程序层确定性判断（任务状态、门禁退出码、事件类型、成员在不在、去重窗口），**不实现**原型 `policy.ts:75` `AdmissionTableSchema` 那种 9 种准入组合。原型那套建立在 GitHub/飞书的高噪声事件流上，我们是本地小团队、事件本来就少而准，照搬就是过度设计。Slow 层（模型语义判定）本期只留接口位置与切换判据，不实现。

**成功判据（一句话）**：队长注入的 sleep 必须被拒且不留等待记录（去掉守卫必红）；注入正文变成 ID + 关联引用且展开能逐字取回原文（总长仍 ≤ 4000）；构造一条「门禁失败」事件必须自动推动且面板原因可读，事件流关闭时退回轮询仍能推进（降级不得静默失效）。

## 2. 用户故事（各带可测验收口径）

1. **作为队长（当前会话）**，我被告知「只分派与验收、不亲自干细活、不同步等长任务」，并且这条约束不依赖我自觉——我调前台长等待会被直接拒绝。
   → 验收：AC-1 / AC-4 / AC-5 / AC-6。
2. **作为用户**，我要能给队长单独指定模型（省钱或换更强的规划模型），并且**它真的生效**；如果不生效，配置界面必须明说，不许让我按账单才发现。
   → 验收：AC-2 / AC-3。
3. **作为成员**，我拿到的团队记忆是「哪几条、怎么关联」，需要细节时按 ID 展开取回原文，而不是拿一段被截断、丢了后半段的正文。
   → 验收：AC-7 / AC-8 / AC-9 / AC-10。
4. **作为用户**，任务因为「A 门禁失败」「B 成员退出」「C 停滞超时」而自动变化时，我要在面板上看到一句人话解释；不该出现「任务自己动了，原因未知」。
   → 验收：AC-13 / AC-17。
5. **作为维护者**，我要能证明这三套机制真的在起作用：去掉守卫、把注入改回整段正文，对应断言必须变红。
   → 验收：AC-6 / AC-11 / AC-20。
6. **作为用户**，我讨厌同一件事被通知两次：一次停滞、一次门禁失败都只能推进一次、只出现一条告警。
   → 验收：AC-15 / AC-22。

## 3. 范围与非目标

**范围内**

1. 队长分层：`captainSection` 固化三条硬约束；队长模型的单独指定（含可行性实测与"必失败不假称"）；noWait 类守卫（拒绝同步 `sleep`、拒绝超大输出/同步阻塞等待）。
2. Inline & Spill：记忆注入改为「唯一 ID + 关联 ID + 一行摘要」的内联形态，按需逐跳展开取回原文，总长仍在 4000 字符预算内（不扩大预算）。
3. 内部 Trigger 总线：四类 Trigger（门禁失败 / 成员退出 / 依赖完成 / 超时无产出）从已实测宿主事件（或轮询兜底）产生，经最小 Fast 层过滤后**复用 `bridge.act` 既有语义**推动队长决策；面板可见「因何事件而推进」。
4. 交付：QA-REPORT.md（逐 AC 判定表贴实跑输出）、ACCEPTANCE.md。

**非目标**

- **不做 Slow 层**（模型语义判定 / 独立 assessor session）：只留接口位置与切换判据（AC-19）。
- **不做 9 种准入组合表**（`AdmissionTableSchema` 等价物），不做外部事件源（GitHub/飞书 webhook），不做 SQLite/存算分离/端侧 daemon（`SUPER-AGENT-MAPPING.md §4` 已定不搬）。
- **不顺手改上期 3 条 P3**：跨 run 同名 binding 的 progress 泄漏（`src/host/index.ts:195` name 兜底）、peer 实发失败无重投、`store.list` 随 run 数线性增长。本期改动不得夹带这三项（AC-22 断言）。
- **不做真机视觉复核**：由主 agent 装 profile 后单独进行，本期只做 DOM/快照级断言。
- 不改数据模型主干：不新增路由、不新增 `PanelAction` 类型、不新增 `ActivityEvent.kind` 枚举值（沿用既有 9 个 kind 与 11 个 action）。

## 4. anti-goals / 反面目标

技术上都跑通了、门禁全绿，但下面任何一条成立，这个需求就算失败：

1. **守卫把正常工作也拦了**：队长跑 `npm test`（文件里含 `sleep` 字面量）、或 `bash -c 'sleep 0.1'` 探活被拒，队长只能换命令绕过去。症状：一次 run 里出现 ≥1 次「合法命令被守卫拒绝」，且拒绝对成员 session 也生效。
2. **Inline 之后信息反而更少**：「注入里只剩一堆 ID，展开回来是截断的半截，或者要展开 3 层才拿到一句结论」。症状：成员在同一次任务里 ≥2 次问「记忆里到底写了什么」/ 展开返回 `truncated=true` 却没有任何指示。
3. **动作来源不可解释**：面板上任务自己推进了，但一行原因都看不到；或原因只写 `gate_failed` 这种码，用户不知道该去看哪条门禁、谁的退出码。症状：一条 Trigger 推进的活动事件里，`text` 不含实体 id 或不含可读中文短语。
4. **同一 episode 双份**：一次门禁失败在面板出现两条告警 / 两次推进（r4 已踩过「事件 + 轮询叠加」这个形态）。症状：同一 (kind, taskId, 时间桶) 在活动流里出现 2 条。
5. **队长模型假装生效**：配置里填了队长模型、快照显示已生效，实际仍跑宿主默认。症状：用户从 token 账单或模型回显里发现不一致——这比"不支持"糟得多。

## 5. 交互流程摘要

**A. 队长守卫（同步阻塞）**

队长发起 `bash`（或等价工具）调用 → 守卫在**执行前**判定：是否前台同步等待（`sleep` / 显式等待）且 ≥ 阈值 → 是则拒绝返回可读原因码（命令不执行、不产生等待记录）→ 队长收到拒绝后改用后台或 `agent` 派发；否则原样放行。守卫只作用于队长 session，成员 session 完全不受影响。

**B. Inline & Spill（记忆）**

派发/续聊成员 → `selectMemory` 选候选（项目轨优先、标题命中优先……顺序不变）→ 每条压成「`mem://<id>` + 标题 + 轨道 + 一行摘要 + 关联 ID 列表（≤3 个）」→ 拼进 4000 字符预算（超预算时**减少条目数与摘要长度**，不截断正文、不再打 `…[截断]`）→ 成员需要细节时按 ID 展开；展开可跳一次（关联 ID），跳数上限 2；被省略的条目不是丢失，而是"未被内联但可展开"。

**C. Trigger 总线（事件为主、轮询兜底）**

宿主事件（`tools/result` / `agent/status` / `subagent/end` / `agent/error`）→ 归一成 Trigger `{kind, source, runId, taskId?, memberId?, at, dedupeKey}` → Fast 层（纯程序）：事件类型是否在监听集合 → 任务/成员是否存在且状态合法 → 门禁退出码是否为 0 → 去重窗口内是否已推进 → `accepted`（带 reason）或 `dropped`（带 reason，**不产生任何 spawn/消息/状态变更**）→ accepted 走 `bridge.act` 既有 action（`dispatch` / `receipt` / `resume` / `message` 等），并在活动事件里写一条可读原因「因 X 事件（实体 id）推进：<结果>」，`source: 'trigger'` 与用户点击的 `'user'` 可区分。事件订阅不可用时，watcher 的 1500ms tick 承担同类判定（依赖完成 / 停滞），快照标 `degraded: true`。

## 6. 优先级

- **P0（缺一不可，决定本期是否成立）**：AC-1、AC-4、AC-5、AC-6（队长守卫 + 变异自检）；AC-7、AC-8、AC-9、AC-11（Inline 结构 + 预算 + 展开 + 变异自检）；AC-12、AC-13、AC-14、AC-15、AC-16、AC-18（Trigger 探针/映射/Fast/幂等/复用语义/降级）；AC-20、AC-21、AC-22、AC-23（预算不破 + 全量门禁 + 不回归 + 报告）。
- **P1**：AC-2、AC-3（队长模型与实测结论）、AC-10（展开降级与路径逃逸）、AC-17（面板可读原因）。
- **P2**：AC-19（Slow 层留位）、展开跳数上限可调、面板原因文案折叠形态。

## 12. 术语

- **队长（captain）**：当前 DSH 会话本身，负责拆解、派发、验收；不亲自执行细活。
- **成员（member）**：`agentTeams.spawnTeammate` 起的可续聊子 Agent。
- **noWait 守卫**：拒绝队长发起「前台同步长等待」的机械拦截（原型 `ROUTER_PRESET` 的同类物）。
- **Inline & Spill**：常驻上下文只放"指针"（唯一 ID + 关联 ID + 摘要），正文按需展开；spill 指被移出常驻上下文、可按 ID 取回的那部分内容。
- **Trigger**：内部事件归一后的推进信号，四类：门禁失败 / 成员退出 / 依赖完成 / 超时无产出。
- **Fast 层**：对 Trigger 的纯程序判定（accepted / dropped + reason），零模型调用。
- **Slow 层**：模型语义判定（本期不实现，只留位置与切换判据）。
- **episode**：同一实体（task/member）同一性质的一次事件过程，是幂等与告警去重的粒度。
